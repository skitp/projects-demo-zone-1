**Architecture: Chatbot → Azure Blob Storage → Event-driven Fabric Notebook (email with PDF attachment)**

This design uses native Microsoft Fabric capabilities (Real-Time hub + Activator) for the trigger so the existing notebook runs automatically when a PDF lands in the predetermined path. The Fabric workspace already has private endpoint access to the storage account, which is leveraged for secure reads.

### High-Level Flow
1. **Chatbot** generates one or more PDFs and uploads them to a fixed container/path in Azure Blob Storage (e.g., `chatbot-pdfs/output/{conversation-or-request-id}.pdf`).
2. **BlobCreated** event is emitted by the storage account.
3. Fabric Real-Time hub receives the Azure Blob Storage events.
4. **Activator** rule (with path filter) triggers the existing Fabric notebook, optionally passing the blob path as a parameter.
5. Notebook reads the PDF over the private endpoint and sends the email with the file as an attachment (using its existing capability).

### Prerequisites
- Azure Storage account kind **StorageV2** (or Block Blob / Blob Storage). General-purpose v1 is not supported for Event Grid / Fabric Azure events.
- **Microsoft.EventGrid** resource provider registered on the subscription (if not already).
- Fabric workspace on capacity or trial with Contributor (or higher) rights.
- Existing notebook that can send emails with attachments (SMTP, Microsoft Graph, Logic App/Power Automate call, or other method already implemented).
- Private endpoint connectivity from the Fabric workspace to the storage account already in place (workspace identity or managed identity recommended for authentication).
- Storage account and Fabric region compatibility with the Azure Blob Storage events connector (certain regions are unsupported—check current docs).
- If workspace outbound access protection or private links are enabled, configure the necessary exceptions / trusted resources for Real-Time events and Event Grid system topics.

### Step-by-Step Enablement

**1. Chatbot / PDF Generation & Upload Layer**  
Implement (or confirm) the chatbot backend so that PDF generation ends with an upload to the predetermined path.  
Typical options:
- Azure Bot Service / Copilot Studio + Azure Function or App Service backend.
- Custom web app or Teams bot calling a Python/Node service that uses libraries such as `reportlab`, `fpdf2`, `weasyprint`, or Azure Document Intelligence / OpenAI-assisted generation.
- Upload via Azure SDK (`azure-storage-blob`) or REST using a service principal, managed identity, or SAS scoped to the target container/path.

Use a consistent naming convention (timestamp, conversation ID, request ID) so the notebook can identify the file if needed. Prefer the Blob endpoint for events (`Microsoft.Storage.BlobCreated`).

**2. Confirm Storage Account Event Support**  
Ensure the account is StorageV2 (or equivalent supported kind). Event Grid system topics or subscriptions are created automatically when Fabric connects, but you can pre-register the provider if desired.

**3. Bring Azure Blob Storage Events into Fabric Real-Time Hub**  
- Switch to the Fabric workload if needed.  
- Go to **Real-Time** → **Azure events** (or Data sources → Azure events).  
- Select **Azure Blob Storage events** → **Set alert** (or Connect / Create eventstream first if preferred).  
- Choose the subscription and storage account.  
- Select event types: at minimum **Microsoft.Storage.BlobCreated**.  
- Add a filter on the **subject** field so only the predetermined path fires the rule, for example:  
  - Subject **begins with** `/blobServices/default/containers/<your-container>/blobs/<your-predetermined-folder>/`  
  - Optionally add “does not contain” filters for subfolders you want to exclude.  
- Save the source/eventstream as required by the wizard. This creates the necessary Event Grid linkage and Fabric eventstream/Activator scaffolding.

**4. Configure Activator Rule to Trigger the Notebook**  
In the same Set Alert flow (or by editing the Activator item later):  
- **Condition**: “On each event” (or more selective if needed).  
- **Action**: Run Fabric item → select **Notebook** → choose your existing email notebook.  
- **Parameters** (supported): Pass dynamic event properties. Map the `subject` (full path) or derived blob name/URL to a notebook parameter (e.g., `blobPath` or `blobUrl`). Use the `@PropertyName` or similar dynamic content syntax shown in the UI.  
- **Save location**: Choose or create an Activator item in an appropriate workspace.  
- Create the alert/rule and start it if it is not auto-started.

The notebook can now receive the path and download only the newly created PDF.

**5. Update / Verify the Existing Notebook**  
- Add or confirm a parameter cell (e.g., `blobPath` or `blobUrl`) that Activator populates.  
- Use the workspace’s private endpoint access (workspace identity, managed identity, or existing connection) to download the blob. Example patterns: `notebookutils` / `mssparkutils`, Azure Storage SDK with DefaultAzureCredential, or ABFS/WASB path if configured.  
- Reuse the existing email-sending logic and attach the downloaded PDF (or stream it directly).  
- Handle edge cases: multiple PDFs in one run, missing files, retry/logging, and cleanup if desired.  
- Test the notebook manually with a sample path first.

**6. End-to-End Testing**  
- Generate a test PDF via the chatbot (or manually upload a file to the exact path).  
- Confirm the BlobCreated event appears in the Real-Time hub stream.  
- Verify Activator fires and the notebook run appears in the Monitor hub.  
- Confirm the email arrives with the correct attachment.  
- Validate private endpoint traffic and that public access is not required.

### Key Design Notes & Alternatives
- **Path filtering is critical** so only chatbot-generated files (not other blobs) trigger the notebook.  
- Passing the `subject` as a parameter is the cleanest way for the notebook to know exactly which file to attach.  
- If parameter passing is limited in your environment, alternatives include: trigger a short Pipeline that receives the event and calls the notebook with parameters, or have the notebook list recent blobs in the folder (less precise).  
- For multiple PDFs, the chatbot can write a manifest JSON alongside them, or the notebook can process all new files matching a pattern.  
- Security: Prefer managed/workspace identity over connection strings. The existing private endpoint already satisfies network isolation.  
- Monitoring: Use Fabric Monitor hub, Activator rule history, and Azure Storage diagnostics / Event Grid metrics.  
- Cost/scale: Activator + notebook runs only on actual events (no polling). Large PDFs or high volume may need capacity or concurrency considerations.

This pattern keeps the chatbot independent, uses native Fabric eventing (no custom Azure Function required for the trigger), and reuses your existing email notebook while respecting the private endpoint setup. Adjust the exact filter string and parameter names to match your container and notebook signature.
