Below is a production-oriented star schema for the FNOL liability payload. It preserves the claim-level grain, handles repeating entities such as people and incident types, separates PII from general claim attributes, and avoids turning the dynamic fields[] array into an unmanageable wide table.

A star schema is appropriate because the central fact represents the FNOL business event, while dimensions provide descriptive context for filtering and analysis. This is also the recommended modeling pattern for Microsoft Fabric Warehouse and Power BI semantic models.

1. Recommended business process and grain
Business process

First Notice of Loss, or FNOL, submission

Primary fact grain

One row in FactClaimFNOL per submitted FNOL reference.

For the supplied payload:

reference = GT-d658adab
grain     = one row for this submitted FNOL


Do not make one row per JSON field the primary analytical fact. That would make basic claim reporting difficult and require repeated filtering and pivoting.

Some child objects have separate grains:

One row per person involved in a claim
One row per incident type selected for a claim
One row per property damage item, when item-level details become available
One row per original captured field, retained for audit and lineage

5. Audit table for original JSON fields

A pure star schema is not sufficient for traceability because:

The questionnaire can evolve.
value and values have different structures.
unanswerable and other_value may be analytically relevant.
Corrected or standardized attributes must remain traceable to the source.

Use this supporting audit table outside the presentation star.

AuditClaimField

Grain: One row per source claim field value. For arrays, use one row per array element.

Column	TypeClaimReference	VARCHAR(50)
FieldKey	VARCHAR(200)
FieldLabel	VARCHAR(1000)
FieldValueOrdinal	INT
FieldValue	VARCHAR(8000)
SourceChannel	VARCHAR(50)
UnanswerableFlag	BIT
OtherValue	VARCHAR(4000)
RawValueType	VARCHAR(20)
IngestedAtUTC	DATETIME2(6)

For liability_incident_type, create three audit rows with ordinals 1, 2, and 3.

This table should not normally be exposed directly to business users. It is primarily for reconciliation, schema-evolution analysis, lineage, and troubleshooting.

8. Data-quality rules identified from the payload

Create exceptions rather than silently resolving these conditions:

Business-name inconsistency
 Copper Kettle Bistor versus Copper Kettle Bistro.

Surname inconsistency
 Structured name is Nadia Whitfeld, while the email contains whitfield.

Derived injury severity
 “Moderate Injury” is present as a structured value but was not independently characterized by the reporter.

Derived preferred language
 “English” is present as a structured value but was not independently stated.

Age-versus-DOB ambiguity
 The field accepts age or DOB, and the supplied value is 34. Store it as AgeAtLoss, not as a date.

Duplicate person roles
 Regina Alvarez is both reporter and primary contact. Nadia Whitfeld is both injured person and property owner. Resolve each person once and assign multiple bridge roles.

Payload-level versus nested LOB
 Validate that root line_of_business equals payload.line_of_business. Quarantine the record if they disagree.

9. Recommended semantic model relationships

Use single-direction, one-to-many relationships from dimensions to facts:

DimDate[DateKey]                 1 -> * FactClaimFNOL[LossDateKey]
DimDate[DateKey]                 1 -> * FactClaimFNOL[SubmittedDateKey]
DimPolicy[PolicyKey]             1 -> * FactClaimFNOL[PolicyKey]
DimLocation[LocationKey]         1 -> * FactClaimFNOL[LossLocationKey]
DimLineOfBusiness[LOBKey]        1 -> * FactClaimFNOL[LOBKey]

FactClaimFNOL[ClaimFNOLKey]      1 -> * BridgeClaimParty[ClaimFNOLKey]
DimParty[PartyKey]               1 -> * BridgeClaimParty[PartyKey]
DimPartyRole[PartyRoleKey]       1 -> * BridgeClaimParty[PartyRoleKey]

FactClaimFNOL[ClaimFNOLKey]      1 -> * BridgeClaimIncidentType[ClaimFNOLKey]
DimIncidentType[IncidentTypeKey] 1 -> * BridgeClaimIncidentType[IncidentTypeKey]


For DimDate, use role-playing views or duplicated semantic-model date dimensions for:

Submission Date
Loss Date

This keeps report filtering predictable.

10. Final recommendation

Use FactClaimFNOL as the primary reporting fact, supported by FactClaimInjury and FactClaimPropertyDamage. Model parties once in a secured DimParty, then associate them to claims through role-based bridges. Preserve every original questionnaire response in AuditClaimField, but do not use the field-value structure as the main reporting model.

This design provides:

A clear and stable claim-level grain
Support for multiple incident types
Support for multiple parties and overlapping party roles
PII isolation
Historical policy and party changes
Questionnaire schema evolution
Source-to-curated traceability
Straightforward Power BI reporting
Design improvements

The model separates analytically useful business entities from the dynamic questionnaire representation, prevents role-based party duplication, and explicitly preserves uncertain or conflicting source values instead of silently standardizing them.
