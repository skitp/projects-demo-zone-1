Proposed FNOL Ingestion Solution
Executive Summary

Leverage the existing Platform Ingestion Service to ingest FNOL JSON documents into a Raw/Bronze layer and use a configuration-driven mapping framework (YAML/JSON) to transform the semi-structured payload into the dimensional model.

The solution supports both:

Event-driven ingestion (storage event on file creation)
Batch ingestion (scheduled processing)

without requiring code changes for future FNOL questionnaire changes.

Configuration-Driven Mapping Framework

Instead of hardcoding field extraction logic, maintain mappings in YAML or JSON.

Example YAML Configuration
source:
  entity: fnol_claim

grain:
  target_fact: FactClaimFNOL
  business_key: reference

mappings:

  - source: policy_number
    target: DimPolicy.PolicyNumber

  - source: business_name
    target: DimPolicy.BusinessName

  - source: date_of_loss
    target: FactClaimFNOL.LossDateKey
    transformation: date_key

  - source: loss_state
    target: DimLocation.StateName

  - source: reporter_name
    target: DimParty.FullName
    role: REPORTER

  - source: primary_contact_name
    target: DimParty.FullName
    role: PRIMARY_CONTACT

  - source: injured_person_name
    target: DimParty.FullName
    role: INJURED_PERSON

  - source: injury_severity
    target: DimInjurySeverity.InjurySeverityName

Event-Based Processing
Recommended Default

Producer drops file into storage.

Example:

/fnol/bop-liability/2026/09/08/file.json


Storage event generated:

Blob Created


Event triggers Platform Ingestion Service.

Flow:

Blob Created
    ↓
Ingestion Service
    ↓
Validate JSON
    ↓
Persist Raw
    ↓
Apply Mapping Config
    ↓
Load Dimensions
    ↓
Load Facts

Benefits
Near real-time claims intake
Lower latency
Minimal operational effort
Supports high claim volumes

Schema Evolution Support

Questionnaires will inevitably change.

Example

New field appears:

{
  "key":"weather_conditions",
  "value":"Rain"
}


No ingestion code changes required.

Only mapping update:

- source: weather_conditions
  target: DimWeather.Condition


or

- source: weather_conditions
  target: FactClaimFNOL.WeatherCondition


This is one of the biggest advantages of a metadata-driven ingestion framework.

Data Quality Layer

Add configurable validation rules.

Example:

validations:

  - field: policy_number
    required: true

  - field: date_of_loss
    required: true

  - field: reporter_email
    format: email

  - field: rating
    range:
      min: 1
      max: 5


Failed records routed to:

FNOL_Quarantine

Recommended End-State

Implement a metadata-driven FNOL ingestion framework on top of the existing Platform Ingestion Service:

Raw/Bronze layer stores original JSON.
YAML/JSON mapping configuration drives transformations.
Event-based ingestion is the default pattern using Blob Created events.
Batch ingestion remains available through configuration.
Dimension and fact loading populate the curated star schema.
Feedback payloads are ingested as a separate fact linked to the claim.
Validation and quarantine provide operational control.
Schema evolution is handled through configuration updates rather than code changes.

This approach aligns well with your existing Common Ingestion pattern and keeps future FNOL questionnaire changes largely configuration-driven rather than requiring notebook or pipeline modifications.
